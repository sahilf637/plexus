# Plexus M2 — LLM enrichment

## Context

M0 and M1 capture anything and link it by meaning, offline. M2 lets a connected AI provider add
what local models can't: real titles, one-line summaries, concepts, and links that say *how* two
items relate, with a reason. Everything here is optional: with no provider connected, Plexus
behaves exactly as before.

Decided (2026-10-05):
- **Providers**: OpenAI-compatible first (covers OpenAI, Groq, OpenRouter, Ollama, LM Studio,
  so fully local use works), then Anthropic and Gemini. Keys live in the system keychain.
- **Only new items** are enriched. Existing libraries are not touched automatically; a later
  "deeper linking" mode (a button, or slow background work) feeds the same queue through its
  low-priority lane, so nothing here needs redesigning for it.
- **Titles**: an AI title replaces only a title Plexus made itself (first line, address, file
  name), never one the user changed. It is marked as AI-made and can be reverted.
- **Images** are described by a vision-capable model; the description goes in the note like OCR
  text, so the image then links by what it shows.

## Structure: two axes, not a stack of layers

- **Tree (where an item lives)**: Area → Topic → Sub-topic → Item, one variable-depth tree built
  from clusters in M3. Depth follows library size; "subject" is just the top level. Not built in
  M2, but M2 produces what M3 needs to name clusters cheaply (summaries and concepts).
- **Mesh (how items connect)**: item ↔ item typed links, and item → concept tags. Concepts cut
  across topics ("borrow checker" appears under Rust and under systems programming).

Concepts are chips and a map highlight, not nodes on the map. Sources, dates and people are
filters on items, not layers. Cluster membership is never decided by the AI, only named by it
(M3), so topics stay stable.

## What gets built

### Backend

- `llm/`: one blocking HTTP client (`ureq`) behind a `Client` that dispatches to `openai`,
  `anthropic` or `gemini`. Each takes the same `Request` (system + user text, optional images,
  a JSON schema) and returns parsed JSON. Errors are classified (`Auth`, `RateLimited`,
  `Unavailable`, `Bad`) so the queue knows whether to retry, wait or pause.
- `llm/keys.rs`: the API key in the OS keychain (`keyring`), never in files or the database.
- `settings.ai`: on/off, a list of named **connections** (preset, provider kind, base URL, model,
  vision on/off), which one is in use, and a daily call limit. No key in here: each connection's
  key is in the keychain under the connection's id (the single provider of the first M2 build
  becomes a connection named after its preset, so its saved key still works). A key is never
  sent over plain `http://` to another computer.
- `db/concepts.rs` + migration 6: `concepts` (name, embedding), `concept_aliases`,
  `item_concepts`, `enrichment` (cache by content hash + version), and `items.summary`.
- `enrich/`: the T2 stage.
  - `queue`: two lanes (new items first, backfill after), pause/resume, daily budget, status
    events. A run of failures pauses it instead of hammering a broken key.
  - `context`: builds the bounded call: the item (head plus sampled excerpts if long, capped),
    about 15 candidate cards from hybrid retrieval (similar links, nearest vectors, keywords),
    about 30 concepts (those of the candidates, then nearest by embedding). Candidates and
    concepts go in as short aliases (`c1`, `k1`) and answers are mapped back; anything not shown
    is dropped.
  - `apply`: validates the answer and writes it: AI title into the note (frontmatter marks it
    `title_by: ai`, `title_was`), summary and concepts into the index, typed edges
    (`provenance = 'llm'`) with reasons and confidence.
  - Skips items flagged as secrets or whose content hash was already sent (`enrichment` cache).
  - Images first get a vision call whose description is written into the note (`vision@1`),
    then the item is linked again and enriched as text.
- Edges: typed kinds `supports`, `contradicts`, `extends`, `example_of`, `similar`; `src` is the
  item the statement is about ("src extends dst"). When a pair has both a local and an AI link,
  readers get one merged edge (AI type and reason, stronger tier).
- Undo: `revert_title` restores the old title and locks it; `reject_link` hides one AI link and
  stops it coming back (`status = 'rejected'`).
- Commands: AI settings, key set/clear, test connection, enrichment status, revert/reject.
  Events: `item-enriched` (concepts) and the existing `item-updated` / `links-changed`.

### Frontend

- Settings: a sidebar (General, Capture, AI, Library). AI lists the providers (pick the one in
  use, remove) and "Add provider" opens a short form: provider, key, model (a dropdown filled from
  the provider), optional name. The provider is checked with a tiny request before it's kept, so
  a wrong key never gets added. A pencil on each row opens the same form to change the name, model
  or key (empty key = keep the saved one); the provider kind stays, so to switch provider, remove
  it and add another. The address is not exposed; each preset has its own.
- Item panel: a bar that stays on top while the note scrolls (kind, the title once its heading has
  scrolled away, open/delete/close), summary, concept chips (click highlights them on the map), link type and reason
  on each related row, "AI" mark on a title with Revert, remove on AI links.
- Map: highlight by concept; header indicator while enriching ("Reading 3 more…", paused,
  or an error with a way to fix it).
- Mock backend: simulates enrichment so `npm run dev:ui` shows all of it.

## Bounded context

Per call, regardless of library size: item ≤ ~8,000 characters, ≤ 15 candidate cards (title plus
one line), ≤ 30 concept names, a fixed output schema. Never the corpus. Never an item flagged
as a secret. Never the same content version twice.

## Order

1. Docs (this file).
2. `llm/` and keychain, Settings connect + Test.
3. Migration, concepts store, enrichment cache.
4. Enrichment stage: titles, summaries, concepts, typed links, queue.
5. Frontend and mock.
6. Vision for images.
7. Tests; update `CLAUDE.md` and `docs/OVERVIEW.md`.

## Status

All steps are implemented, with the mock backend standing in for a provider in `npm run dev:ui`.
Differences from the plan: a long item is cut to its start plus three evenly spaced passages
(not summarised chunk by chunk), since summarising each chunk would cost a call per chunk; the
AI's `similar` type was dropped in favour of `related` (plain "similar" is what local linking
already says); titles are renamed on disk only for notes without originals beside them. Not
tried against live providers in development: the request shapes are covered by tests against a
local fake server (`llm::http_tests`), so the first real call per provider is the real check.

Not here, by design: enriching existing libraries (later: a "deeper linking" button or slow
background pass through `Lane::Backfill`), topics (M3).

# Plexus M5 — scale

## Context

M0–M4 and P1 are built and feel fast on a few hundred notes. M5 makes the same app work with
tens of thousands of notes, and (with some limits) hundreds of thousands. This file starts with
the **baseline**: what the code does today on a synthetic library, so each change can be judged by
numbers. The plan follows once the baseline has been read.

## A. How it was measured

Nothing here is a guess from reading the code; each row comes from one of two harnesses (both
in the repo). The library is synthetic: notes in clusters of about 60, 1 to 8 chunks each
(about 3 on average), 384-dimension vectors that fall into clusters, about 5 links per note,
a concept for every 8 notes, a topic tree. A laptop with 4 cores and 7 GB of memory, release
build (`opt-level 3`, no LTO).

**Backend** — `backend/src/scale.rs`, an ignored test that times what the app does, against the
real index code (no model needed):

```bash
cd backend
PLEXUS_SCALE_N=50000 PLEXUS_SCALE_OUT=/path/out.json cargo test --release scale_report -- --ignored --nocapture
PLEXUS_SCALE_N=20000 cargo test --release scale_reconcile -- --ignored --nocapture   # real files on disk
```

`PLEXUS_SCALE_OUT` writes the timings as JSON, to compare before and after a change. The scratch
index goes in `backend/target/scale-data` (not `/tmp`, which may be memory).

**Frontend** — `npm run scale-map -- 50000` writes a made-up map to `frontend/public/map.local.json`;
open `/?map=map.local.json` (`npm run dev:ui`, or better a production build, whose numbers are
much lower than dev mode's). With that file loaded, `__mock.emit(event, payload)` in the console
sends events (`item-linked`, `item-added`) so their cost can be timed. The browser here is the
mock backend, so loading includes parsing the JSON but not Tauri's own transfer.

## B. Baseline (before any M5 change)

Backend, per operation, by library size (notes):

| | 10k | 50k | 100k |
|---|---|---|---|
| **Capture**: write the note into the index | 12 ms | 64 ms | 109 ms |
| Store its chunks and vectors (background) | 10 ms | 57 ms | 132 ms |
| One nearest-neighbour search (40 chunks) | 28 ms | 127 ms | 230 ms |
| Link a note (about 3 chunks) | 144 ms | 375 ms | 978 ms |

| Place a new note in a topic (`assign`) | 17 ms | 89 ms | 204 ms |
| Rebuild the topic tree | 2.8 s | 20 s | 42 s |
| – of which reading every vector | 0.6 s | 5.1 s | 13.9 s |

| – size sent to the UI | 14 MB | 69 MB | 137 MB |

Fine as it is (not worth touching yet): keyword search (60 ms at 100k), Ask's exact search over
every note (160 ms at 100k), comparing all concepts for an enrichment (23 ms at 100k).

## C. What the numbers say

1. **Capture breaks its 50 ms promise** at about 30–40k notes. The note's keyword-search row is
   removed by `item_id`, which the full-text table doesn't index, so every save scans the whole
   table (checked separately: 4 ms at 10k rows, 40 ms at 100k).
2. **Every vector search reads every vector**, linearly (28 → 127 → 230 ms), and linking does one per
   chunk. At 1M notes one search would be a couple of seconds and one link tens of seconds.
3. **Importing is quadratic**, on both sides: `assign` loads every topic and membership per
   note (204 ms each at 100k), and in the UI each linked note rebuilds every link on the map
   (3.3 s each at 50k). An import of 10k notes would freeze the map for over an hour.
4. **Opening the map** is the whole library in one message (137 MB at 100k) and the UI takes
   30 s for 50k.
5. **While a note links, everything else waits** for the index (1.9 s at 100k), because the link
   job holds the one database connection.

## D. Plan

Decided order (each step is measured against section B):

1. Remove the quadratic and per-note full-library work, no new ideas: fix the keyword-search
   delete, `assign`, `older::pick`, the map's per-note work (links, colours, sizes, hover grid,
   topic layer), reconcile; give reads their own connections.
2. Replace the scan with an index for nearest-neighbour search, and link per note rather than
   per chunk.
3. Slice the map by topic: show topics when zoomed out, load notes and links as you zoom in.
4. Make topic rebuilds local instead of whole-library.

Each step records its numbers here when done.
